Configuration

One list of sites, shared by the command line and the VS Code extension, plus per-machine state that never leaves the computer.

Where things are kept

Settings roam with your user profile; state stays on the machine. sync-servers config path prints the folders in use.

Folders per platform
PlatformSettings (sites.json)State and logs
Windows%APPDATA%\sync-servers%LOCALAPPDATA%\sync-servers, logs in its logs folder
macOS~/Library/Application Support/sync-serversits state folder; logs in ~/Library/Logs/sync-servers
Linux and other systems$XDG_CONFIG_HOME/sync-servers, else ~/.config/sync-servers$XDG_STATE_HOME/sync-servers, else ~/.local/state/sync-servers

SYNC_SERVERS_HOME moves both: settings to that folder and state to its state subfolder. --config-dir and --state-dir move one for a single command. Folders are created private to you (0700 on Linux and macOS).

What the state folder holds
PathHolds
sites/<site id>/<server id>.jsonThe sync records: both sides of every file as they were at its last synchronization.
sites/<site id>/hashes.jsonThe scan cache of file hashes, used in checksum mode.
recovery/<site id>/<run>/Local files a run deleted or overwrote, kept 14 days by default.
logs/run-*.jsonlOne log per run, the newest 30 kept, with every secret removed.

The list of sites

sites.json is plain JSON, described by a JSON Schema that editors use for completion. Every write is atomic, keeps the previous version as sites.json.bak, and takes a lock file so two programs never lose each other's changes. A file that does not validate is never rewritten. Edit it with the commands, the terminal interface, or sync-servers site edit --editor, which reopens your editor with the problems listed until the JSON is valid.

{
  "$schema": "https://isocialpractice.github.io/cmd-sync-servers/schema/site.schema.json",
  "schemaVersion": 1,
  "sites": [
    {
      "id": "3f2b7c1e-8a4d-4f6b-9c2e-1d5a7b9e0c31",
      "name": "My Site",
      "localRoot": "/home/<user>/sites/my-site",
      "servers": [
        {
          "id": "9a1c3e5f-7b2d-4e6a-8c0f-2b4d6e8a0c13",
          "name": "Production",
          "protocol": "sftp",
          "host": "sftp.example.com",
          "username": "demo-user",
          "auth": { "method": "password", "savePassword": true },
          "remoteRoot": "/var/www/my-site",
          "webUrl": "https://www.example.com/"
        }
      ],
      "remoteServerId": "9a1c3e5f-7b2d-4e6a-8c0f-2b4d6e8a0c13",
      "cloaking": { "patterns": [".psd", "node_modules/"] }
    }
  ]
}

Fields left out take their defaults. Passwords never appear in this file.

Cloaking

Cloaked files and folders are never scanned, listed, transferred or deleted, on either side. Patterns use the rules of .gitignore files, with one addition for suffixes:

Cloaking patterns
PatternCloaks
.psdEvery name ending in .psd: a token that starts with a dot and has no * or / is a suffix.
archive*Every file or folder whose name starts with archive, at any depth.
node_modules/Every folder named node_modules, and everything in it.
/drafts/Only the drafts folder at the top of the site.
!keep.psdUncloaks what an earlier pattern cloaked.

Names are matched ignoring case on Windows and macOS. Single paths can be cloaked too, and cloak everything beneath them:

sync-servers cloak .psd "archive*" node_modules/    # patterns
sync-servers cloak img/raw                          # an existing path in the site
sync-servers cloak --list
sync-servers uncloak .psd

The sensitive-file guard

Some files are almost never meant to be published. A file matching one of these patterns is listed in the preview unchecked with the pattern it matched, and moves only when you check it. It is never hidden.

.env  .env.*  *.pem  *.key  *.p12  *.pfx  *.kdbx  id_rsa*  id_ecdsa*  id_ed25519*
.git/  .hg/  .svn/  .ssh/  .aws/  .npmrc  .pypirc  .netrc  *.sqlite-journal

Add patterns of your own in sync.guard.patterns or the Security category of Site Setup. Unattended runs with --yes never transfer a guarded file.

Secrets

Passwords and key passphrases are never written to a file. When a connection needs one, it is looked for in this order:

  1. The operating system's credential store, when the server has savePassword on: Windows Credential Manager, the macOS Keychain, or the Secret Service keyring on Linux. Entries use the service sync-servers.
  2. The environment: SYNC_SERVERS_PASSWORD, or SYNC_SERVERS_KEY_PASSPHRASE for a key.
  3. A question in the terminal, typed without being shown. With nobody to ask, the run fails with E_AUTH.
sync-servers password set Production --site "My Site"     # save it
printf %s "$SECRET" | sync-servers password set Production --stdin
sync-servers password forget Production                    # remove it

A secret is asked for only after the server's host key or TLS certificate has been verified, and it is removed from every log and error message. A saved secret is tied to the protocol, address, port and user it was saved for; after any of them changes, it is no longer sent and you are asked again, so save it again with password set. SYNC_SERVERS_KEYRING=off turns the credential store off.

Which site a command means

A command acts on the site named by its argument or --site, then SYNC_SERVERS_SITE, then the site whose local folder holds the current folder (the deepest one when sites are nested). In a terminal, you are otherwise asked to choose; in a script, the command stops with a usage error that lists the sites.
