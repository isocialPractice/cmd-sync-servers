Synchronization

How a sync finds what changed on each side, decides what each file needs, and runs only what you confirm.

To put only the files you worked on in the last hours or days, see Putting the files of a time range.

The memory of the last sync

For every file it synchronizes, sync-servers records both sides as they were at that moment: the size and modification time of the local copy and of the server copy. These sync records are kept per site and server in the state folder of this computer.

On the next sync each side is compared with its own record, never with the other side's clock. A local file whose size or time moved is changed locally; a server file whose size or time moved is changed on the server. When both moved, the file changed on both sides, and it waits for your decision instead of being overwritten. A local file is held to its record exactly, since the disk reports the same time for a file nobody touched. On the server, times closer than the tolerance, 2 seconds by default, count as equal, because many servers round them in listings.

A file with no record yet, as on a first sync, is compared across the two sides: the newer copy wins, and copies of the same age that differ ask for a decision. In checksum mode (sync.compare set to checksum) SHA-256 hashes settle what times cannot.

One file is never compared at all: _notes/dwsync.xml, where Dreamweaver keeps its own records of a folder. It is never a row of a preview, on either side.

A site that Dreamweaver synchronized has a memory already, in those files. With sync.dreamweaver.enabled on, sync-servers reads an entry as evidence for a file both sides have: when both copies are as Dreamweaver last recorded them, the file is in sync, and when only one is, the other side changed. So the first preview of such a site lists only real differences, and a file put with Dreamweaver between two syncs is not a conflict. A file that is missing on one side is never judged by an entry, so an entry never checks a delete. After each transfer the entry is written the way Dreamweaver would have written it, a delete removes it, and the entries of other servers stay as they are, so both programs go on agreeing. The records of sync-servers itself stay the ones it trusts: removing a _notes folder loses nothing here.

Dreamweaver reads a server's clock its own way, so nothing is taken from its records, or written to them, until sync-servers knows the difference. It learns it from the entries during the first synchronization of the whole site, when at least three files agree, and accepts one hour either way for daylight time.

sync-servers status shows what changed on each side without planning anything. mark-synced records files as in sync without moving them, and state reset forgets the records so the next sync starts from scratch.

The delete option

With --delete, or the delete checkbox, a file missing on the other side is offered for deletion instead of being copied back. The checkbox is worded for the direction: Delete remote files not on local drive when putting, Delete local files not on remote server when getting.

A file that was never synchronized is only ever offered for deletion unchecked: nothing is deleted just because it has no record.

Put and Get of single files

sync-servers put css/site.css and get move the files and folders you name at once, through the same checks. When one of them changed on the other side, or is held back by the guard, the preview opens first so you can decide.

Putting the files of a time range

Sometimes only the work of the last hours or days should go to the server: on a site with other differences that are not ready to go yet, or on one that was never synchronized, where a Put lists every file. A time range puts just the files you worked on lately:

sync-servers sync --put recent --range 2d

The range is a number and one unit in lower case, counted back from now. -r is short for --range, the word recent may be left out, and paths after it keep the range to those folders and files, as in sync-servers sync --put recent -r 90m css.

The units of a time range
UnitCountsExample
mMinutes--range 90m, the last 90 minutes
hHours--range 24h, the last 24 hours
dDays--range 2d, the last two days
wWeeks--range 1w, the last week

The number may have a decimal part, as in 1.5h. A capital letter, another unit or two ranges at once are refused, so 2M is never taken for two minutes.

  • What recent means. A file is recent when it was created or last modified at or after the start of the range, by this computer's clock and the dates its file system keeps. A file copied into the site keeps the modification time it came with, and still counts from the day it arrived. Folders are not judged, only the files in them.
  • What the preview holds. The recent files that differ from the server, each as in any preview: one that also changed on the server waits for a decision, and one that matches a sensitive pattern is held back. Recent files already in sync are counted as skipped, and cloaked files are left out as always.
  • What it never holds. A delete, a Get, or a file only the server has. A range goes with Put only, and not with the delete option.
  • What the server is asked. Only the recent files are looked up on the server, file by file, and nothing connects when no file is recent. That is quick for a few files. When the range takes in most of a large site, sync --put without a range, which compares whole folders, is faster.
  • Time on disk. A file counts by the time it was saved to disk. One that is open in an editor with unsaved changes counts by its last save.

The preview is titled for the range, such as Put files from the last 2 days, and from there everything is as in any synchronization: check or uncheck rows, then confirm. In a terminal, sync-servers sync without a direction offers Put files from a time range as its first choice and asks for the range, with 1d as the answer Enter gives. The Synchronize screen of the terminal interface has the same choice.

The preview

The preview lists only files with a difference; unchanged files are counted, never listed. A preview made from a time range lists only the recent ones among them. Its summary line counts what will happen, such as Files: 37 will be updated, 169 will be skipped, 12 need a decision. Each row has a checkbox, an action and a status that says why, in a sentence:

Rows that start unchecked
RowWhy
ResolveChanged on both sides, or differs with no record. Choose an action first.
GuardedMatches a sensitive pattern such as .env; see the guard.
Never-synchronized deleteOffered by the delete option for a file with no record.
ProblemA name that cannot be used here: not valid on this system, a symbolic link that is not followed, or two names that differ only by case on a file system that cannot tell them apart. Problem rows never run.

You can change any row: check or uncheck it, or choose another action that the file can take. Put needs a local copy, Get a server copy, and Synchronized both.

Running a plan

  • Checked once more. Just before a file moves, both sides are looked at again. A file that changed since the preview is skipped and reported as stale.
  • Written whole or not at all. A file is written to a partial copy, its size checked, and only then renamed into place, so an interrupted transfer never leaves half a file.
  • Local files kept. A local file that a run deletes or overwrites is moved to the recovery folder of the state folder first, and kept 14 days.
  • Through links. When the site follows symbolic links, a Get through a link writes the file the link points to and keeps the link, and rows that reach one file through two names run one at a time.
  • Folders in order. Folders are created before their files and removed after them.
  • Retries. A dropped connection or a timeout is retried on a fresh connection after 1, 2 and 4 seconds.
  • Recorded as it goes. Records are saved during the run, so a cancelled or interrupted sync keeps what it finished. Cancelling starts no new transfer and removes partial files.
  • Recorded when nothing moves. A synchronization with nothing to transfer still records the files it found to be the same on both sides, so the next one does not compare them from scratch. --dry-run and status record nothing.

Safety guards

Some plans stop before anything moves, with exit code 5:

  • Mass delete. Deleting more than 50 files, or more than a quarter of a side's files, asks you to type the count. A script needs --allow-mass-delete. Both limits are settings of the site.
  • Empty root. When one side is empty and the plan would delete everything on the other, the run is refused: an unmounted drive or a wrong root directory looks exactly like that.
  • Top of a server. Deletes are refused when the server's root directory is / or a drive root, unless the server allows it with allowRootDeletes.
