Security

sync-servers moves your files with your credentials. This page says what it protects against, how, and what stays your job.

Principles

  • Secure by default. SFTP is the default protocol, certificates are verified, and the unsafe choices are opt-in with a warning every time.
  • Nothing moves unseen. Every synchronization is previewed. Scripts see the preview and change nothing unless they pass --yes.
  • Nothing is lost silently. Deletes need an explicit option, large deletes need the count typed back, and local files that a run replaces are kept.
  • Secrets never touch a file. Not the settings, not the logs, not an error message.
  • A server is not trusted with your disk. Names a server returns are checked before they become local paths.

Protocols

What each protocol protects
ProtocolProtection
SFTPEncrypted and authenticated by SSH. Only modern key exchange, host key, cipher and MAC algorithms are offered. A server that needs older ones must set legacyAlgorithms, and every connection to it warns.
FTPSTLS 1.2 or later, with the certificate chain and host name verified against the system's certificate authorities, plus a private one given with --ca-file.
FTPNone: the password and every file travel in clear text. Refused unless the server sets allowInsecure, and every connection warns.
Local folderWhatever the drive or network share provides.

Host keys

An SSH host key proves you reached the right server. The first connection to a server shows its fingerprint, such as ssh-ed25519 SHA256:..., and asks whether to trust it. Compare it with the fingerprint your host publishes before you answer.

  • Trust and remember pins the key in the server's settings. From then on, a different key stops the connection with E_HOST_KEY_MISMATCH and shows both fingerprints. It is never accepted silently.
  • Trust for this connection only pins nothing.
  • An unattended run never trusts an unknown key on its own. Pass the expected fingerprint with --host-key SHA256:<fingerprint>.
  • When a server's key changes for a good reason, check the new fingerprint with the server's administrator, then sync-servers server edit Production --forget-host-key and connect again.

Credentials

  • Passwords and key passphrases are kept only in the operating system's credential store, when you choose to save them. They are never written to sites.json, a log, a plan file or a temporary file.
  • A password is asked for, and sent, only after the server's host key or TLS certificate has been verified.
  • Every secret is registered with the logger the moment it is read and replaced with [redacted] in every log line and error message, including FTP PASS commands and passwords inside URLs.
  • Private keys are read from their file when connecting and never copied.
  • For scripts, SYNC_SERVERS_PASSWORD supplies the password. Treat it like the password itself: keep it in your CI system's secret store.

Safe deletes and overwrites

  • Nothing is deleted without the delete option. A file that was never synchronized is only ever offered for deletion unchecked.
  • Deleting more than 50 files, or a quarter of a side, needs the count typed back, or --allow-mass-delete in a script.
  • A plan that would delete everything because one side is empty is refused, since an unmounted drive or a wrong root looks exactly like that.
  • Deletes at the top of a server (/ or a drive root) are refused unless the server allows them.
  • Each file is checked again just before it moves; one that changed since the preview is skipped.
  • Files are written to a partial copy and renamed into place only when complete.
  • Local files a run deletes or overwrites are kept in the recovery folder for 14 days.
  • Sensitive files such as .env, private keys and credential folders are held back unchecked, and never moved by an unattended run.

A server you do not fully trust

A compromised or malicious server can return any names it likes. Before a name becomes a local path it is checked:

  • The names . and .., and names with a slash, a control character, or more than 255 bytes, are refused and listed as problems.
  • Names that are not valid on Windows, such as CON, name. or a name with : or a backslash, are refused on Windows.
  • Two names that differ only by case are both refused on a file system that cannot tell them apart.
  • Writes never follow a symbolic link or junction out of the site.
  • A folder listing with more than 100,000 entries is refused, so a server cannot exhaust memory.
  • Control characters in names and messages are shown escaped or as ?, never sent to your terminal.

What stays on your computer

  • Settings, sync records, the scan cache, the recovery folder and the logs are created private to you (0700 folders and 0600 files on Linux and macOS).
  • Logs record what happened and never file contents. The newest 30 run logs are kept.
  • The temporary files of a diff and of editor mode live in a private temporary folder and are removed when done.
  • Nothing is sent anywhere but to your servers: no analytics, no update checks.

What stays your job

  • Checking a host key fingerprint before trusting it.
  • Keeping your computer account, your credential store and your CI secrets safe; anyone who controls your user account controls your saved passwords.
  • Choosing SFTP or FTPS. Plain FTP cannot be made safe.
  • Reviewing the preview, especially rows held back by the guard and deletes.

Reporting a vulnerability

Report it privately through GitHub's private vulnerability reporting. Never open a public issue for a vulnerability. Include the version, the operating system and the Node.js version, the steps that reproduce it and the impact as you understand it, with placeholders such as sftp.example.com instead of real hosts or passwords.

You get an acknowledgement within 7 days and an assessment within 14. Fixes ship as a new alpha with a published advisory that credits you, unless you ask not to be named. The full policy is in SECURITY.md.
